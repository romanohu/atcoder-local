# AtCoderローカルワークフロー改善設計

## 概要

既存の `acc` ラッパーを入口として維持し、C++のビルド、手動実行、サンプルテスト、提出前検証、環境診断を一貫したコマンドで実行できるようにする。

既存のatcoder-cliとonline-judge-toolsは、コンテスト情報取得、サンプル取得、提出などの外部サービス接続に引き続き利用する。リポジトリ側は、対象問題の解決、コンパイラ選択、ローカルライブラリ、bundle、検証順序、安全な提出確認を担当する。

## 目標

- `acc build`、`acc run`、`acc test`、`acc submit`、`acc doctor` を提供する。
- 問題ディレクトリ内とリポジトリルートの両方から同じ操作を実行できるようにする。
- C++を標準言語としつつ、将来ほかの言語バックエンドを追加できる境界を設ける。
- ローカルの共通ヘッダーを分割して管理し、提出時には自己完結した単一ファイルへ変換する。
- AtCoder Library 1.6を固定して同梱し、ローカルと提出時のバージョン差をなくす。
- 誤提出、失敗したbundleの提出、古いバイナリの実行を防ぐ。
- macOS/Linuxのbashとzshをサポートする。
- 新規クローン後の環境構築と診断をREADMEだけで再現できるようにする。

## 対象外

- atcoder-cliによるコンテスト作成、タスク取得、認証処理の再実装
- online-judge-toolsによるサンプル実行、提出通信の再実装
- Windows対応
- 保存時の自動再テスト（watch mode）
- C++以外の言語バックエンドの実装
- ACLに含まれるデータ構造やアルゴリズムの独自再実装
- グラフ、数学、文字列アルゴリズムを網羅する独自ライブラリ
- CLI提出失敗時のブラウザ起動、URL表示、クリップボード操作
- 非対話提出や確認を回避する `--yes` オプション

## 既存リポジトリとの関係

現在の `tools/acc_wrapper.py` は、atcoder-cliへ引数を委譲し、`acc new` 成功後に `memo.md` の生成とコンテスト期間中のpush lock登録を行う。既存の通常コマンド委譲、memo生成、push guardの動作は維持する。

現在の開発依存関係には `pytest` がなく、READMEどおりの `uv sync` 後にテストを起動できない。この不足も本変更で修正する。

atcoder-cli 2.2.0の `acc submit` は、対象URLとファイルを解決した後、内部でonline-judge-toolsの提出処理を呼び出す。AtCoderは提出時のCAPTCHAを導入しており、開催中のRatedコンテストではCAPTCHAなしで提出できる方針を示しているが、将来にわたる保証はない。そのため、CLI提出は失敗し得る外部処理として扱い、失敗時には終了コードとエラーをそのまま返す。

## アーキテクチャ

### コマンド振り分け

シェル上の `acc` 関数は、現在と同じくPythonラッパーを呼び出す。`tools/acc_wrapper.py` は先頭のサブコマンドを調べ、次の規則で処理する。

- `build`、`run`、`test`、`submit`、`doctor` は新しいワークフローモジュールへ渡す。
- `new`、`add`、`config` など、それ以外のコマンドはインストール済みのatcoder-cliへ渡す。
- `new` 成功後のmemo生成とpush lock登録は、現在の順序と失敗時の扱いを維持する。

### ファイル構成

```text
tools/
├── acc_wrapper.py
└── atcoder_workflow/
    ├── __init__.py
    ├── cli.py
    ├── context.py
    ├── compiler.py
    ├── cpp.py
    └── commands.py

library/
├── atcoder/
└── atcoder_local/
    ├── core.hpp
    ├── io.hpp
    └── debug.hpp
```

各モジュールの責務は次のとおりとする。

- `cli.py`: カスタムサブコマンドの引数解析、エラー表示、終了コードへの変換
- `context.py`: リポジトリ、コンテスト、問題、ソース、テストディレクトリの解決
- `compiler.py`: コンパイラの検出、種別と版の確認、通常・デバッグ用フラグの構築
- `cpp.py`: C++のコンパイル、bundle、実行に必要な低水準処理
- `commands.py`: 各コマンドの処理順序と停止条件

外部プロセス実行は共通の差し替え可能な境界を通す。単体テストでは実際の `acc`、`oj`、`oj-bundle`、C++コンパイラを起動せず、構築された引数、入出力、終了コードを検証できるようにする。

## 対象問題の解決

### 問題ディレクトリ内

現在位置から親方向へ最寄りの `contest.acc.json` を探す。その設定内で、現在位置に一致するタスクディレクトリを特定する。

一致するタスクがない場合、複数のタスクに一致する場合、設定が不正な場合はエラーにする。ディレクトリ名だけからコンテストIDやタスクIDを推測しない。

### リポジトリルート

`-c/--contest` と `-t/--task` の両方を必須とする。片方だけの指定はエラーにする。

例:

```sh
acc test -c abc123 -t a
```

リポジトリ以下の `contest.acc.json` を検索し、JSON内の `contest.id` が `-c` の値と一致する設定を使う。一致する設定が複数ある場合は曖昧としてエラーにする。グローバルなatcoder-cliのディレクトリ形式設定には依存しない。

`-t a` は選択した `contest.acc.json` 内のタスクラベルと大文字小文字を区別せず照合し、atcoder-cliへ渡せる完全な問題ID（例: `abc123_a`）へ変換する。指定コンテストの設定またはタスクが見つからない場合はエラーにする。

明示された `-c/-t` は現在位置からの自動検出より優先する。

C++ソースは、対象タスクの `directory.submit` に記録された相対パスから解決する。現在のテンプレートでは `main.cpp` になる。設定がない場合や、解決先がタスクディレクトリの外へ出る場合はエラーにする。

## コマンド契約

### `acc build`

対象タスクの提出用C++ソースを通常設定でコンパイルする。成功した実行ファイルは次の場所へ保存する。

```text
.atcoder-local/build/<contest-id>/<task-id>/main
```

コンパイル失敗時は非ゼロで終了し、以前の成功成果物を今回の成果物として扱わない。

### `acc run`

通常設定でビルドした後、標準入力、標準出力、標準エラーを端末へ接続して実行する。プログラムの終了コードをコマンドの終了コードとして返す。

### `acc test`

通常設定でビルドした後、対象タスクの `test/` を指定して `oj test` を実行する。テストケースがない場合はエラーにする。

`acc test --debug` はSanitizer付きのデバッグ設定でビルドしてから、同じサンプルテストを実行する。

### `acc submit`

次の処理を順番に実行する。

1. `oj-bundle` にリポジトリ内ライブラリのincludeパスを渡し、`submission.cpp` を一時ファイルへ生成する。
2. bundleが成功した場合だけ、正式な提出候補へ置き換える。
3. `submission.cpp` を通常設定でコンパイルする。
4. bundle後の実行ファイルを使って全サンプルを実行する。
5. コンテストID、問題ID、提出ファイルを表示し、対話端末で提出確認を求める。
6. 明示的な承認を受けた場合だけ、インストール済みatcoder-cliの `acc submit` に `submission.cpp`、コンテストID、完全な問題IDを渡す。

確認の既定値はNoとする。bundle、コンパイル、テスト、確認のいずれかが失敗または拒否された場合は提出しない。非対話端末では確認を省略せず、提出不可としてエラーにする。

atcoder-cliによる提出がCAPTCHAや認証状態などの理由で失敗した場合、ブラウザ起動、URL表示、クリップボード操作は行わない。atcoder-cliの終了コードとエラーを返す。

### `acc doctor`

次の項目を検査する。

- Pythonとuvからプロジェクト依存関係を実行できること
- インストール済みatcoder-cliをPythonラッパーの内側から呼び出せること
- `oj` と `oj-bundle` が利用可能であること
- C++23を受け付けるコンパイラが見つかること
- 同梱ACL 1.6と独自ヘッダーが存在すること
- push guardが現在のリポジトリへインストールされていること
- bash/zshラッパーファイルが存在し、ラッパーが子プロセスへ渡す `ATCODER_LOCAL_WRAPPER=1` マーカーを現在の呼び出しで確認できること

必須項目の欠落はエラーとし、非ゼロで終了する。AtCoderの現行GCCとの差など、基本操作を妨げない差分は警告として表示する。

## C++コンパイラ

コンパイラは次の順序で選択する。

1. `CXX` 環境変数で明示された実行ファイル
2. GCC 15として確認できる実行ファイル
3. 利用可能な `g++`
4. 利用可能な `clang++`

実行ファイル名だけで種別と版を判断せず、`--version` の出力を確認する。候補がC++23の最小スモークコードをコンパイルできない場合は使用しない。

通常設定では次を必須フラグとする。

```text
-std=gnu++23 -O2 -Wall -Wextra -DONLINE_JUDGE -DATCODER
```

これにリポジトリの `library/` を指すincludeパスを加える。`build`、`run`、通常の `test`、提出前ビルドは同じ必須フラグを使用する。

デバッグ設定では次を必須フラグとする。

```text
-std=gnu++23 -O0 -g -Wall -Wextra -DATCODER -DLOCAL
-fsanitize=address,undefined -fno-omit-frame-pointer
```

`ONLINE_JUDGE` はデバッグ設定では定義しない。選択されたコンパイラが必要なSanitizerに対応しない場合は、黙って通常ビルドへ戻さずエラーにする。

## C++ライブラリとテンプレート

### AtCoder Library

AtCoderの現行環境に合わせ、公式ACL 1.6を `library/atcoder/` 以下へ固定して同梱する。ライセンスと取得元をリポジトリ内に記録する。セットアップ時のネットワーク取得や、マシンごとの別途インストールには依存しない。

### 独自共通ヘッダー

初期版では次の小さな補助だけを提供する。

- `core.hpp`: `ll` などの型エイリアス、`rep`、汎用的な `chmin/chmax`
- `io.hpp`: 高速I/O初期化と小さな入出力補助
- `debug.hpp`: `LOCAL` ビルドでのみ有効になるデバッグ出力

各ヘッダーにはinclude guardを付け、単独でも依存関係が明確になるようにする。ACLが提供するDSU、Fenwick Tree、セグメント木などは再実装しない。

`template/cpp/main.cpp` は基本の独自ヘッダーだけを読み込む。ACLは問題ごとに必要なヘッダー、または `<atcoder/all>` を利用者が追加する。テンプレートはC++固有バックエンドを前提とするが、ワークフロー全体の対象解決とコマンド処理は将来の別言語バックエンドから再利用できるようにする。

## 依存関係とシェル対応

- `online-judge-tools` と `aclogin` は既存の通常依存関係として維持する。
- `online-judge-verify-helper` を通常依存関係へ追加し、`oj-bundle` を `uv sync` で導入する。
- `pytest` を開発依存関係へ追加する。
- zsh用ラッパーとbash用ラッパーを用意し、どちらも同じPythonエントリーポイントを呼び出す。
- ラッパーは利用者の `.zshrc` や `.bashrc` を自動編集しない。
- READMEには、一時的な `source` と恒久設定用の絶対パス指定を分けて記載する。

## 生成物と更新の安全性

生成物は `.atcoder-local/` 以下へまとめ、Gitの管理対象外とする。

外部コマンドはシェル文字列ではなく引数配列として起動する。コンパイル結果とbundle結果は一時ファイルへ出力し、成功後に目的のパスへ置き換える。失敗後に以前の成功バイナリや提出候補を自動実行しない。

素のatcoder-cliへ委譲するコマンドでは、標準入力、標準出力、標準エラー、終了コードを維持する。

## エラー処理

次の状態は明確なエラーメッセージと非ゼロ終了にする。

- リポジトリまたは `contest.acc.json` を特定できない
- 対象タスクを一意に特定できない
- `-c` と `-t` の片方だけが指定された
- 設定された提出用C++ソースまたは `test/` が存在しない
- コンパイラ、`oj`、`oj-bundle`、atcoder-cliが利用できない
- C++23またはSanitizerの能力確認に失敗した
- bundle、コンパイル、サンプルテストが失敗した
- 提出が非対話端末から呼び出された
- 提出確認が拒否または中断された
- atcoder-cliによる提出が失敗した

エラーメッセージは、失敗した段階、対象コンテスト・問題、利用した主要パスを含める。認証情報やCookieの内容は表示しない。

## テスト戦略

### 単体テスト

- 問題ディレクトリからの対象解決
- ルートからの `-c/-t` 解決とラベル変換
- 不正・不足・曖昧な指定の拒否
- コンパイラ候補の優先順位、種別、版の判定
- 通常・デバッグ用コンパイル引数
- 各外部コマンドの引数構築
- 提出確認のYes、No、中断、非対話
- `acc doctor` のエラーと警告の分類

### ワークフロー結合テスト

一時リポジトリへ最小の `contest.acc.json`、`main.cpp`、サンプルを配置し、偽の外部コマンドを注入して処理順序と終了コードを検証する。

特に、`acc submit` がbundle、bundle後コンパイル、bundle後テスト、確認のすべてに成功した場合だけatcoder-cliを呼ぶことを確認する。各段階を個別に失敗させ、後続処理が呼ばれないことも確認する。

### C++スモークテスト

利用可能な実コンパイラを使い、次を検証する。

- 各独自ヘッダーを単独でincludeできる
- 独自ヘッダーを使う最小プログラムをビルド・実行できる
- ACLの代表機能を使う最小プログラムをビルド・実行できる
- `oj-bundle` で生成した単一ファイルを再コンパイル・実行できる

### 回帰テスト

既存の `tests/test_acc_wrapper.py`、push guardの単体テストとGit結合テストを維持する。通常コマンドの委譲と `acc new` 後のmemo生成・push lock登録が変わらないことを追加で確認する。

## 受け入れ条件

- 問題ディレクトリ内で5つのカスタムコマンドを対象指定なしで実行できる。
- リポジトリルートで `-c` と `-t` を指定して同じ操作を実行できる。
- `acc test` は通常ビルド、`acc test --debug` はSanitizer付きビルドを使用する。
- `acc submit` はbundle後のコードを再コンパイル・再テストし、対話確認後だけ提出する。
- CLI提出失敗時にブラウザ、URL案内、クリップボード操作を行わない。
- ACL 1.6と独自ヘッダーをオフラインで利用できる。
- GCC 15を優先し、利用できない場合は別コンパイラへフォールバックして差異を診断できる。
- bashとzshの両方から同じPythonワークフローを呼び出せる。
- 生成物はGitへ追加されない。
- 既存のmemo生成とpush guardのテストを含む全テストが成功する。
- 新規クローンからREADMEの手順だけで環境を構築し、`acc doctor` で不足を確認できる。
